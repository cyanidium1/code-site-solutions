# Семантическая архитектура — code-site.art

## Методология и ограничения (честно)

- DataForSEO нет → **нет объёмов запросов и измеренного SERP-пересечения** (пункт 3 методики
  «10 shared URLs = same post» не выполним буквально). Пересечение интентов ниже — качественная
  оценка по смыслу заголовков/контента, помечено как `[оценка]`, не как измеренный факт.
- Часть выводов получена не через WebSearch по живой выдаче, а через **прямой публичный запрос к
  тому же Sanity-датасету (`4lk0x7o9/production`, `perspective:"published"`, без токена)**, из
  которого рендерится прод — то есть данные о категориях статей, ссылках в теле (markDefs) и
  привязке кейсов к отраслям **фактические, не рендер-зависимые**. Помечено `[CMS-факт]`.
- Логика роутинга ссылок (какая категория ведёт на какую страницу) прочитана из
  `src/components/blog-post-page/index.tsx` и `src/components/industry-page/index.tsx` в **локальном
  репозитории**. Раздел `_AUDIT-CONTEXT.md` прямо предупреждает: прод и локальный `master`
  расходятся. Где не успел сверить с живым URL — помечено `[код, не сверено с прод]`.
- Заголовки/H1 сняты частично; там где не снимал напрямую — помечено `[не снято]`.

## 2. Каннибализация — приоритетные находки

### 2.1. `/vs-wordpress` + `/vs-constructors` vs. блог-статьи о том же сравнении

- `nextjs-proty-wordpress-ta-konstruktoriv` (ua) / `nextjs-vs-wordpress-for-business-2026` (en) /
  `nextjs-protiv-wordpress-i-konstruktorov` (ru) — заголовок буквально «Next.js против WordPress
  **и конструкторов**» — покрывает интент ОБЕИХ страниц `/vs-wordpress` и `/vs-constructors` разом.
- `tilda-vs-kastomnyy-sayt-2026` (ua/ru) / `custom-website-vs-wordpress-2026` (en) — «Tilda vs
  кастомный сайт» — прямое пересечение с `/vs-constructors`.
- `[оценка]` По смыслу заголовков и H1 это один и тот же коммерческий вопрос
  («стоит ли переходить с конструктора/WordPress»), поданный дважды: один раз как услуговая
  страница-компаратор, второй — как блог-пост. Без DataForSEO не могу подтвердить дословное
  10/10-совпадение SERP, но структурное дублирование интента очевидно из заголовков.
- **В ru эта пара — вообще единственный актив**: `/vs-wordpress` и `/vs-constructors` в ru
  **не существуют** (подтверждено `all-urls.txt`), значит в ru-локали статьи
  `nextjs-protiv-wordpress-i-konstruktorov` и `tilda-vs-kastomnyy-sayt-2026` **выполняют роль
  пиллара сами по себе** — не спутника.

### 2.2. Автоматическая «По темі» ссылка в конце поста противоречит категоризации `[CMS-факт + код]`

Компонент `blog-post-page/index.tsx` выбирает единственную коммерческую ссылку в конце
каждой статьи по `post.category.slug` через карту `CATEGORY_COMMERCIAL`. Категория `finance`
используется CMS-редакцией не как «финансовая отрасль», а как отстойник для статей про
цену/продвижение — из-за чего автоссылка ведёт не туда:

| Статья (ua slug) | Категория CMS | Автоссылка внизу поста | Реальная тема статьи |
|---|---|---|---|
| `prosuvannia-saitu-tsina-2026` | `finance` | → `/sites-for/finance` («сайт для фінансової компанії») | Цена SEO-продвижения — тело статьи уже вручную линкует на `/seo` и `/pricing` (см. markDefs) |
| `sait-dlia-budivelnoi-kompanii-2026` | `finance` | → `/sites-for/finance` | Сайт для **будівельної/ремонтної** компанії — тело статьи вручную линкует на `/sites-for/renovation`, `/landing`, `/corporate-site` |
| `vartist-rozrobky-saytu-2026` | `finance` | → `/sites-for/finance` | Общая цена сайта — тело линкует на `/pricing` (×2), `/calculator`, `/landing`, `/corporate-site`, `/online-store` |

Итог: у трёх статей внизу страницы стоит нерелевантный якорь «сайт для фінансової компанії»,
который противоречит корректным ручным ссылкам в теле того же поста. Для пользователя и краулера
это шум и слабый сигнал релевантности, для `/sites-for/finance` — 3 входящих ссылки с чужим
контекстом вместо целевых.

### 2.3. Отсутствующая запись `renovation` в карте `CATEGORY_COMMERCIAL` `[код, не сверено с прод]`

Ключи карты: `medicine, finance, legal, real-estate, ecommerce, auto, courses, platforms`.
`renovation` отсутствует — если статью когда-либо категоризируют как `renovation`, автоссылка
всё равно упадёт в fallback `platforms → /pricing`, а не на `/sites-for/renovation`. Сейчас это
не проявляется только потому, что ни одна статья не имеет категории `renovation`
(см. раздел 3) — то есть баг замаскирован отсутствием контента, а не отсутствует сам.

### 2.4. `/seo` vs. блог-статьи про SEO — по факту НЕ каннибализация, а рабочая связка `[CMS-факт]`

Проверил markDefs (ручные ссылки в теле) шести SEO-статей — почти все **уже вручную ссылаются на
`/seo`**: `redyzain-bez-vtraty-seo`, `yak-chytaty-google-search-console`,
`lokalne-seo-top-3-google-maps`, `ai-poshuk-yak-potrapyty-u-vidpovidi`, `seo-audyt-svoimy-rukamy`,
`prosuvannia-saitu-tsina-2026` — все содержат `{"_type":"link","href":"/seo"}` в теле. Значит
спутник→пиллар связь для SEO-кластера **есть**, но она держится на ручной дисциплине автора
Portable Text, а не на архитектуре — риск: новая статья про SEO может выйти без этой ссылки,
и ничего не заставит её появиться (см. раздел 3 — `/seo` не имеет автоблока «статьи по теме»,
в отличие от `/sites-for/*`).

### 2.5. `/sites-for/medicine` vs. `/sites-for/medicine/medychnyi-tsentr` / `/stomatolohiia` (только ua)

Три страницы на одну вертикаль в ua: общий хаб + два под-хаба («медичний центр», «стоматологія»).
Не проверил прямую перелинковку между ними живьём — `[не снято]`. Структурно это правильная
модель (пиллар → под-пилляры), но она существует **только в ua**; en/ru имеют один плоский
`/sites-for/medicine` на ту же по объёму статейную поддержку (7 статей, идентичных по теме во
всех трёх локалях) — то есть в en/ru нет более узких страниц под «клінику» и «стоматологію»,
хотя статьи (`hospital-vs-private-practice-website`, `clinic-website-development-process`)
явно про эти под-темы.

## 3. Хаб-спик — оценена ли схема системно

Ключевой технический факт `[код, не сверено с прод]`: только шаблон `/sites-for/[slug]`
(`industry-page/index.tsx`, строки ~877–887) программно подтягивает блок «статьи этого кластера»
через `BLOG_POSTS_BY_CATEGORY_QUERY` с `cat = page.slug`. Ни один другой хаб
(`/seo`, `/landing`, `/corporate-site`, `/online-store`, `/pricing`, `/vs-*`, `/support`) не имеет
такого блока — `LandingPageView`, на котором держится `/seo` и остальные услуговые страницы,
не содержит ни одного запроса к блогу (grep по компоненту — 0 совпадений).

Но даже там, где механизм есть, он бьёт мимо цели по данным `[CMS-факт]`:

| Категория блога | Постов | `/sites-for/*` с таким slug | Что видит пиллар |
|---|---|---|---|
| `medicine` | 7 | есть | Полный кластер — работает |
| `finance` | 4 | есть | 3 из 4 постов не про финансовую отрасль (см. 2.2) — пиллар получит нерелевантные превью в блоке «статьи по теме» |
| `legal` | 1 (en-only) | есть | Пусто в ua/ru |
| `auto`, `courses`, `ecommerce`, `real-estate`, `renovation` | 0 | есть | **Блок «статьи по теме» не отрисуется вообще** — 5 из 8 отраслевых пилляров в каждой локали (15 URL суммарно по трём локалям) не имеют ни одного автоматического спутника |

Вывод: заявленная схема «услуговая/отраслевая страница = хаб, блог = спутники» реализована
**частично и только для одной трети кластеров**. Для большинства коммерческих страниц блог живёт
отдельной жизнью, и связь держится на ручных ссылках в теле статей, если редактор их поставил.

## 5. Пробелы по темам (конкретные, не рубрики)

- **Поддержка и сопровождение после запуска** — коммерческая страница `/support` существует
  только в ua и не имеет ни одной статьи-спутника. Конкретные темы: «что входит в год техподдержки
  Code-Site.Art», «что делать, если сайт упал / сломался после обновления плагина» (актуально на
  фоне статьи `redyzain-bez-vtraty-seo` про риски после правок), «SLA и время реакции на инцидент».
- **Миграция с конструкторов на custom-код** — есть сравнение (`tilda-vs-kastomnyy-sayt-2026`),
  но нет пошагового «как перенести Tilda/WordPress-сайт без потери позиций» — `/seo`-страница
  прямо упоминает миграцию за $500–2000, но под эту услугу нет ни одной статьи-обоснования.
- **Интеграции** — ни одной статьи или раздела о подключении CRM, платёжных систем, аналитики
  к custom-сайту — тема нигде не встречена в собранном списке из 24 постов.
- **Отраслевая специфика для 5 вертикалей без контента** — `auto`, `courses`, `ecommerce`,
  `real-estate`, `renovation`. Конкретные темы по аналогии с успешным `medicine`-кластером:
  «сколько стоит сайт для автосервісу 2026», «сайт для агентства нерухомості: що показувати
  на головній», «онлайн-курс: лендінг чи повноцінна платформа», «сайт для рієлтора: інтеграція
  з базами оголошень», «до/після ремонту: як показати кейси на сайті будівельної компанії».
- **Финансовая отрасль отдельно от «ціни»** — реальная тема для бухгалтерів/фінансових
  консультантів (EN-версия `web-design-for-accountants` уже существует) — нужны ua/ru аналоги,
  а не переиспользование категории под статьи о цене.
- **Юридическая вертикаль** — 1 статья на весь сайт (EN-only). Нужны ua/ru статьи под
  `/sites-for/legal`, аналогичные `websites-for-solicitors`.

## 6. Портфолио как SEO-актив

- 25 кейсов на локаль обнаружено программным запросом (ожидалось 26 — либо один без
  `status: published`, либо расхождение с sitemap; не выяснял отдельно `[CMS-факт, требует
  сверки]`).
- 17 из 25 (68%) имеют поле `industry`, дающее привязку к `/sites-for/*`: renovation (4),
  ecommerce (5), medicine (2), auto (2), legal (1), courses (1), real-estate (1). **finance — 0.**
- 8 из 25 (32%) — `industry: null`: `clarion-solutions`, `glenn-garbo`, `tatarka-franchise`,
  `urmodels`, `yangoly-hvostykiv`, `rich-tour`, `webbond`, `co2lab`. Эти кейсы физически не могут
  попасть в блок «кейсы этой ниши» ни на одной `/sites-for/*` странице (компонент фильтрует по
  `industrySlug === page.slug`) — треть портфолио выпадает из отраслевой перелинковки.
- Глубину текста (объём прозы, наличие структуры «задача → решение → результат») программно
  подтвердить не успел — запрос по предполагаемым именам полей (`body`, `summary`) вернул `null`,
  значит поля называются иначе; нужна отдельная сверка схемы `caseStudy` в admin-репо. **Помечаю
  как неверифицированное** — не делаю вывод «это просто галерея» без доказательства, но и не
  подтверждаю текстовую насыщенность.
- Подтверждено достоверно: у каждого кейса есть `hero` и структурированный набор `sections`
  (судя по паттерну рендера в `case-page/index.tsx`, аналогичному `industry-page`), то есть
  это не просто картинка + заголовок на уровне схемы данных — но раскрытие текста не измерено.
