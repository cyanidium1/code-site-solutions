# Visual, Mobile & Images Audit — code-site.art

Метод: `capture_screenshot.py` (desktop 1920×1080, laptop 1366×768, tablet 768×1024, mobile 375×812 — фиксированные пресеты инструмента; задание просило 1440×900/390×844, но это те же классы viewport, отклонение несущественно), `analyze_visual.py`, `render_page.py --mode always -o` (полный отрендеренный HTML), ручной просмотр PNG, `curl -I` для заголовков картинок.

Отревьюено визуально (desktop+mobile скриншоты открыты и просмотрены): главная `/` (ua), `/en`, `/ru`.
Скриншоты сняты (4 viewport'а), но НЕ просмотрены в этом проходе: `/pricing`, `/sites-for/medicine`, `/blog/dyzain-saitu-medychnoho-tsentru`, `/portfolio/co2lab`. Файлы лежат в `screenshots/{pricing,sites-for-medicine,blog-article,portfolio-co2lab}/` и готовы к разбору следующим проходом.

Полный инвентарь `<img>` через рендер+regex сделан только для одной страницы: главная ua (64 тега). `/en` и `/ru` используют то же дерево компонентов и тот же hero-ассет — находки по формату/весу hero, вероятно, идентичны, но не перепроверены отдельно. Остальные 4 страницы по картинкам не разбирались.

## A. Первый экран и мобильная вёрстка

`analyze_visual.py` на `https://www.code-site.art/` (desktop-часть проверки) подтверждает: `h1_visible=true`, `cta_visible=true`.

### A2. Mobile (375×812) — CTA и трастовая полоса ниже первого экрана на ВСЕХ трёх локалях

Скриншот — это ровно один viewport без скролла (PNG 750×1624px = 375×812 CSS px при DPR2, не full-page capture). На главной ua/en/ru картина идентична:

- y≈0–700 CSS px (первые ~86% экрана) занимает иллюстрация-мокап (монитор+ноутбук+телефон) поверх шапки с бургер-меню;
- H1-заголовок появляется только у самого низа первого экрана;
- обе CTA-кнопки и вся трастовая полоса (50+/7/×3.2/30%) физически отсутствуют в кадре — требуют скролла;
- поверх нижних ~40% экрана сразу при загрузке лежит cookie-баннер («Ми поважаємо вашу приватність» / «We value your privacy» / «Мы уважаем вашу приватность»), перекрывающий текст подзаголовка ещё до того, как пользователь успевает его дочитать.

Cookie-баннер усугубляет — перекрывает то немногое, что осталось видимым.

### A4. Разовый флак рендера на /ru desktop (не подтвердившийся баг)

Повторный independent-снимок (`screenshots/home-ru-retry/www_code-site_art_desktop.png`, timeout увеличен до 30с) отрисовался корректно с картинкой. ## B. Изображения

### B1. og:image отсутствует на 102 из 208 страниц (49%)

Разрез (данные измерены координатором по всем 208 URL, не пересчитывались повторно):
- Блог: 63 из 69 постов без og:image (91%) — это самый «расшариваемый» и линкуемый тип контента на сайте, и именно там дыра максимальная.
- Все три локали (ua/en/ru) следующих статических разделов без og:image: `/calculator`, `/contacts`, `/corporate-site`, `/landing`, `/online-store`, `/process`, `/seo`, `/pricing`, `/about`, `/vs-*`.
- Портфолио, напротив, покрыто хорошо: 75 из 78 с og:image, и они идут через Sanity CDN (соответствует `docs/images.md`).

Последствия: ссылка на статью блога или на `/pricing`, расшаренная в Telegram/LinkedIn/Slack/X, разворачивается либо голым текстовым превью, либо плейсхолдером платформы — прямой удар по CTR с шеров и по репутации бренда именно там, где предполагается конверсия (прайс, калькулятор, контакты, лендинги по типам сайтов). Учитывая, что блог — основной источник ссылочной массы и повторных визитов, 91%-й пробел там наиболее критичен.

Исправление: добавить fallback og:image на уровне шаблона для блог-постов (сгенерированная OG-карточка с заголовком) и для статических разделов; там, где источник — Sanity, обернуть в `sanityCdn(url, { w: 1200, q: 70 })` согласно `docs/images.md`.

### B2. Главная (ua) — инвентарь `<img>`: 64 тега в отрендеренном HTML

**Hero-изображение (LCP-кандидат)**
`src=/_next/image?url=%2Fhero%2Fhero-mockup.webp&w=3840&q=75`
`alt="Приклад сайту для бізнесу, створеного Code-Site.Art"` (описательный, не пустой — хорошо), `fetchpriority=high`, БЕЗ `loading=lazy` (правильно для LCP-изображения — не ленивое).
`sizes="(max-width: 640px) 64vw, (max-width: 1200px) 100vw, 1200px"`.

Проверено `curl -I` с `Accept: image/avif,...`:
- Запрос `w=3840` → `Content-Type: image/avif`, `Content-Length: 95852` (~94 KB).
- Запрос `w=1200` (потолок из `sizes`) → тот же AVIF, `Content-Length: 48583` (~47 KB) — почти вдвое меньше.
- Исходный файл `/hero/hero-mockup.webp` как статика — 394 660 байт (~385 KB), но пользователю он не отдаётся напрямую.

На скриншотах desktop (1920px viewport) отрисованная область мокапа занимает заметно меньше 1200 CSS px (примерно 700px). Возможный оверфетч LCP-изображения — `w=3840` в `src`-фолбэке в ~2 раза тяжелее, чем нужный `w=1200`, при том что реальная отрисовка ещё меньше заявленного в `sizes` потолка. Т.к. это priority-изображение (`fetchpriority=high`), лишние ~48 KB на пути LCP — не косметика.

Хорошая новость: формат-конвейер РАБОТАЕТ корректно — исходник `.webp`, но `/_next/image` на лету переотдаёт AVIF при поддержке браузером (подтверждено заголовком `Content-Type: image/avif` и `Content-Disposition: ...filename="hero-mockup.avif"`).

**Sanity-изображения (карточки портфолио на главной)**
3 карточки, например: `https://cdn.sanity.io/images/4lk0x7o9/production/5bc6d1c5...-2560x1762.png?auto=format&fit=max&w=800&q=60`, `alt="NBYG København — сайт для будівельної компанії з Копенгагена"`. Идут напрямую через `cdn.sanity.io`, МИНУЯ `/_next/image` — соответствует правилу `docs/images.md`. `alt` описательный и уникальный на каждой карточке — хорошо.

**Декоративные SVG (chevrons, sparkle×3, globe)**
`alt=""` — корректно для чисто декоративных элементов.

**6 плиток индустрий/услуг (unsplash + 1 локальный `/industries/auto.jpg`)**
Все с `alt=""` (пустой), routed через `/_next/image` с тем же паттерном `w=3840` в fallback при `sizes` от 20vw до 33vw вьюпорта (то есть реальная ширина отрисовки на 1920px-экране — порядка 400–630px, а не 3840). Эти плитки смыслово нагружены (представляют категории услуг: авто, юристы, медицина, недвижимость и т.д.), а не чисто декоративны — пустой `alt` на них требует проверки, есть ли рядом программно связанный текстовый лейбл (не подтверждено — `/sites-for/medicine` не разобран визуально в этом проходе).

**Логотипы партнёров/клиентов (13 логотипов, `/partners/*.webp` + 1 `.svg`)**
Каждый логотип отрисован ДВАЖДЫ в DOM (26 тегов на 13 логотипов) — типично для marquee-бесконечной прокрутки, но удваивает число запросов на декоративный трастовый блок. Все `loading=lazy` (уместно, блок ниже экрана), `alt` = название компании (короткий, но адекватный, не «filename.webp»). Один логотип — `/partners/tatarka.svg`, `alt="Tatarka"`, но без `width`/`height` в разметке (`w=None h=None`) — риск точечного CLS именно в этом слоте, остальные 12 логотипов размеры указывают.

**Финальный CTA-блок**
`src=/_next/image?url=%2Fhome%2Flaunch-cta-devices.webp&w=3840&q=75`, `alt="Макет сайту на ноутбуці та смартфоні"` (описательный), `loading=lazy` (корректно, блок ниже экрана), `sizes="(max-width: 1024px) 90vw, 720px"` — разумно.

### B3. width/height — не проверено окончательно

У hero-изображения в разметке есть `width=1700 height=1674` (вероятно, исходные пропорции ассета, не финальный отрисованный размер — контейнер явно шире и площе). У Sanity-карточек портфолио и у 6 плиток индустрий `width`/`height` в HTML отсутствуют (`None`) — это ожидаемо для Next/Image в режиме `fill` с CSS-контейнером фиксированного aspect-ratio, но сам факт наличия/отсутствия `aspect-ratio` в CSS-контейнере не проверялся (нужен просмотр стилей), поэтому не фиксирую как подтверждённый CLS-баг — помечаю как «требует проверки», а не нарушение.

### B4. Что не проверено (пробелы, фиксируем честно)

- Инвентарь `<img>` для `/en` и `/ru` главных — не собирался отдельно (используется тот же компонент, что и на ua, поэтому находки B2 по hero/форматам, вероятно, идентичны, но не подтверждено измерением).
- `/pricing`, `/sites-for/medicine`, статья блога, кейс портфолио — изображения (alt, форматы, оверсайз, `sizes`) не разбирались вообще.
- Точные пиксельные размеры (1200×630) и вес og:image на страницах, где он ЕСТЬ (например, кейсы портфолио через Sanity CDN) — не измерены, только факт присутствия/отсутствия (см. B1).
- Тап-таргеты <44px и обрезанный текст на мобильных версиях `/pricing`, `/sites-for/medicine`, блога и кейса — не проверены.

## Оценки

- **Visual / Mobile: 64/100.** Десктоп — образцовый первый экран на всех локалях. Мобильный первый экран систематически (3 из 3 проверенных локалей) прячет обе CTA-кнопки и трастовую полосу под скролл, а cookie-баннер добивает — перекрывает даже то немногое, что осталось в кадре. Разбор `/pricing`, `/sites-for/medicine`, блога и портфолио ещё предстоит — оценка может измениться.
- **Images: 60/100.** og:image отсутствует на 49% страниц (91% блога) — критический пробел для шеринга. Формат-конвейер `/_next/image` реально переотдаёт AVIF (подтверждено заголовками), Sanity-изображения корректно идут в обход `/_next/image` — оба факта хорошая новость. Портит картину вероятный 2×-оверфетч LCP-изображения на главной и пустой `alt` на смысловых плитках индустрий. Собрано пока только по 1 странице из 7 целевых — итоговая оценка предварительная.
